# Dracula public API (migration in progress)

This is an early, read-only API stage. **Do not deploy or switch the app to it yet**: image transfer and Seeker integration are not implemented. The client has an opt-in API mode for testing. The schema is a data-copy staging schema, not a drop-in replacement for Seeker's SQLite database: in particular, its write behavior and SQLite triggers have not been migrated. The live site still uses its exported snapshot, and Seeker still uses its local database.

The API expects MariaDB tables equivalent to the current Seeker catalogue. `GET /v1/events?filter=upcoming&offset=0&limit=30` returns `{items, total, nextOffset}` with filtering before pagination. Filters are `upcoming`, `today`, `tomorrow`, `weekend`, `custom`, `all`, `past`, and `unknown`. A custom filter requires `from=YYYY-MM-DD` and accepts an optional `to`. The legacy `after` cursor form remains available. `GET /v1/events/:id` returns a single public event. `GET /v1/images/:filename` serves an image only while it belongs to a currently public event. `GET /health` reports that the process is running; it does not verify an ongoing database connection.

Like the current export, the catalogue includes events marked `music` with an unknown date or an end date on or after today in Vilnius. It excludes past events and reviews marked unsure or not music. Consequently, the `past` filter currently returns no events. Event responses include a hosted `image_url`. The client has an opt-in API mode for testing, but Seeker writes and image transfer remain unfinished.

Run `npm install` and `npm test` in this folder. Tests use an isolated SQLite fixture to exercise the portable query logic and HTTP routes. The schema was imported into a Hostinger MariaDB staging database from a verified backup, with row counts and SHA-256 comparisons matching all 15 tables. A public-catalogue SQL count matched the local SQLite result. The API process and its prepared statements have not been tested against MariaDB or deployed to Hostinger.

For eventual deployment, configure the variables in `.env.example` in the hosting environment; never put credentials in the client. `IMAGE_DIR` must point to durable storage outside the deployment directory. `PUBLIC_BASE_URL` is the public API origin. Keep the database private and do not deploy until the full migration and security review have been completed.

Experimental write endpoints for event reviews, details, artist decisions and manual prices exist under `/v1/admin/events/:id/`. They are disabled unless a server-side `ADMIN_TOKEN` is configured, require a bearer token, and update related records in a transaction. Use a long, randomly generated token, never expose it in Expo or browser code, and require HTTPS outside local development. These endpoints and their MySQL transactions have not been verified against MariaDB, are not yet used by Seeker, and do not cover imports or AI jobs. Do not enable them on a deployed server until authentication, transport, rate limiting and integration have been reviewed and tested.

`migrate:staging` is an **untested staging-only** transfer tool. It checks the backup manifest, refuses database names without the `_staging` suffix and refuses databases containing tables. It creates the schema and compares every copied row with the SQLite backup. The script does not copy images. Database schema creation is not transactional in MariaDB; a failed run can leave empty tables requiring manual cleanup. Do not point it at production or run it before MariaDB integration testing.

An alternative for an **empty staging database** is `DB_NAME=<database_ending_in_staging> npm run export:staging -- <complete-backup-directory> <new-output-prefix>`. It checks the backup and generates a SQL import file and a separate verification query, without copying images. Both files contain private catalogue information and must be kept out of Git and public directories. Importing the generated SQL into Hostinger's private staging database and running its verification query was tested; the Node-based `migrate:staging` path was not. Never import into a populated database or production.

To prepare images from the same complete backup, run `npm run prepare:images -- <complete-backup-directory> <new-staging-directory>`. It checks the database hash and each referenced image against the backup manifest, then creates a new `images` directory and a checksum manifest. It refuses an existing destination and removes its newly created directory on failure. This prepares local files only; upload and verification on Hostinger remain to be implemented.
