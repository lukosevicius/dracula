# Dracula public API (migration in progress)

This is an early, read-only API stage. **Do not deploy or switch the app to it yet**: image transfer, Seeker integration and client integration are not implemented. The schema is a data-copy staging schema, not a drop-in replacement for Seeker's SQLite database: in particular, its write behavior and SQLite triggers have not been migrated. The live site still uses its exported snapshot, and Seeker still uses its local database.

The API expects MariaDB tables equivalent to the current Seeker catalogue. `GET /v1/events` returns `{items, next}`; pass `after=<next>` for another page and use `limit` from 1 to 100. `GET /v1/events/:id` returns a single public event. `GET /v1/images/:filename` serves an image only while it belongs to a currently public event. `GET /health` reports that the process is running; it does not verify an ongoing database connection.

Like the current export, the catalogue includes events marked `music` with an unknown date or an end date on or after today in Vilnius. It excludes past events and reviews marked unsure or not music. Event responses include a hosted `image_url`; the existing app still expects bundled numeric image IDs and therefore cannot use this API yet. The API has no write or administration endpoints.

Run `npm install` and `npm test` in this folder. Tests use an isolated SQLite fixture to exercise the portable query logic and HTTP routes. The schema was imported into a Hostinger MariaDB staging database from a verified backup, with row counts and SHA-256 comparisons matching all 15 tables. A public-catalogue SQL count matched the local SQLite result. The API process and its prepared statements have not been tested against MariaDB or deployed to Hostinger.

For eventual deployment, configure the variables in `.env.example` in the hosting environment; never put credentials in the client. `IMAGE_DIR` must point to durable storage outside the deployment directory. `PUBLIC_BASE_URL` is the public API origin. Keep the database private and do not deploy until the full migration and security review have been completed.

`migrate:staging` is an **untested staging-only** transfer tool. It checks the backup manifest, refuses database names without the `_staging` suffix and refuses databases containing tables. It creates the schema and compares every copied row with the SQLite backup. The script does not copy images. Database schema creation is not transactional in MariaDB; a failed run can leave empty tables requiring manual cleanup. Do not point it at production or run it before MariaDB integration testing.

An alternative for an **empty staging database** is `DB_NAME=<database_ending_in_staging> npm run export:staging -- <complete-backup-directory> <new-output-prefix>`. It checks the backup and generates a SQL import file and a separate verification query, without copying images. Both files contain private catalogue information and must be kept out of Git and public directories. Importing the generated SQL into Hostinger's private staging database and running its verification query was tested; the Node-based `migrate:staging` path was not. Never import into a populated database or production.
