# Dracula public API (migration in progress)

This is an experimental API stage, with public reads and protected administrative writes. **Do not deploy or switch the app to it yet**: image transfer and Seeker integration are not complete. The client has an opt-in API mode for testing. The schema is a data-copy staging schema, not a drop-in replacement for Seeker's SQLite database: in particular, its write behavior and SQLite triggers have not been fully migrated. The live site still uses its exported snapshot, and Seeker still uses its local database.

The API expects MariaDB tables equivalent to the current Seeker catalogue. `GET /v1/events?filter=upcoming&offset=0&limit=30` returns `{items, total, nextOffset}` with filtering before pagination. Filters are `upcoming`, `today`, `tomorrow`, `weekend`, `custom`, `all`, `past`, and `unknown`. A custom filter requires `from=YYYY-MM-DD` and accepts an optional `to`. The legacy `after` cursor form remains available. `GET /v1/events/:id` returns a single public event. `GET /v1/images/:filename` serves an image only while it belongs to a currently public event. `GET /health` reports that the process is running; it does not verify an ongoing database connection.

Like the current export, the catalogue includes events marked `music` with an unknown date or an end date on or after today in Vilnius. It excludes past events and reviews marked unsure or not music. Consequently, the `past` filter currently returns no events. Event responses include a hosted `image_url`. The client has an opt-in API mode for testing, but Seeker writes and image transfer remain unfinished.

Run `npm install` and `npm test` in this folder. Tests use an isolated SQLite fixture to exercise query logic and HTTP routes. A verified backup was imported into the Hostinger MariaDB staging database, with row counts and SHA-256 comparisons matching all 15 tables. The Node migration script, API process, prepared statements, protected edits and a Vilnius Events page import have also been tested against a disposable local MariaDB 11.4 instance. The API has not been deployed to Hostinger.

`npm run test:mariadb` runs the API integration test against a disposable MariaDB database. It requires `MYSQL_TEST_HOST`, `MYSQL_TEST_PORT`, `MYSQL_TEST_USER`, `MYSQL_TEST_PASSWORD` and `MYSQL_TEST_DATABASE`; the database name must end in `_test` and the database must be empty. The test creates schema and fixture rows and leaves them in place. Never use a staging or production database for this test. This test is skipped by the normal `npm test` command unless `RUN_MARIADB_INTEGRATION=1` is set.

For eventual deployment, configure the variables in `.env.example` in the hosting environment; never put credentials in the client. `IMAGE_DIR` must point to durable storage outside the deployment directory. `PUBLIC_BASE_URL` is the public API origin. Keep the database private and do not deploy until the full migration and security review have been completed.

Experimental authenticated endpoints cover the private event list and individual event reads, reviews, details, artist decisions, manual prices and one-page Vilnius Events imports. They are disabled unless a server-side `ADMIN_TOKEN` is configured, require a bearer token, and update related records in a transaction. Use a long, randomly generated URL-safe ASCII token, never expose it in Expo or browser code, and require HTTPS outside local development. These endpoints are not yet wired into Seeker and do not cover images, MusicBrainz or AI jobs. Do not enable them on a deployed server until authentication, transport, rate limiting and integration have been reviewed and tested.

`migrate:staging` is a staging-only transfer tool. It checks the backup manifest, refuses database names without the `_staging` suffix and refuses databases containing tables. It creates the schema and compares every copied row with the SQLite backup. The script does not copy images. Database schema creation is not transactional in MariaDB; a failed run can leave empty tables requiring manual cleanup. It has been verified against local MariaDB, but not run on Hostinger. Do not point it at production.

An alternative for an **empty staging database** is `DB_NAME=<database_ending_in_staging> npm run export:staging -- <complete-backup-directory> <new-output-prefix>`. It checks the backup and generates a SQL import file and a separate verification query, without copying images. Both files contain private catalogue information and must be kept out of Git and public directories. Importing the generated SQL into Hostinger's private staging database and running its verification query was tested. Never import into a populated database or production. Staging databases created with the previous schema need the `001-auto-increment.sql` migration before new imports; this migration was tested locally and has not been applied on Hostinger.

To prepare images from the same complete backup, run `npm run prepare:images -- <complete-backup-directory> <new-staging-directory>`. It checks the database hash and each referenced image against the backup manifest, then creates a new `images` directory and a checksum manifest. It refuses an existing destination and removes its newly created directory on failure. After transferring the entire directory, run `npm run verify:images -- <staging-directory>` at the destination to check each file and detect missing or extra files. Upload and verification on Hostinger remain to be performed.
