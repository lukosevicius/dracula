# Dracula public API (migration in progress)

The API is deployed at `https://api.dracula.lt` against the Hostinger MariaDB database. The live Dracula client reads its public endpoints, and local Seeker uses bearer-token-protected administrative endpoints. The old SQLite database is retained as a backup. Hosted event and artist reads and an idempotent event review write have been verified; live source imports and AI jobs have not yet been verified end to end.

The API expects MariaDB tables equivalent to the current Seeker catalogue. `GET /v1/events?filter=upcoming&offset=0&limit=30` returns `{items, total, nextOffset}` with filtering before pagination. Filters are `upcoming`, `today`, `tomorrow`, `weekend`, `custom`, `all`, `past`, and `unknown`. A custom filter requires `from=YYYY-MM-DD` and accepts an optional `to`. The legacy `after` cursor form remains available. `GET /v1/events/:id` returns a single public event. `GET /v1/images/:filename` serves an image only while it belongs to a currently public event. `GET /health` reports that the process is running; it does not verify an ongoing database connection.

Like the former export, the public catalogue includes events marked `music` with an unknown date or an end date on or after today in Vilnius. It excludes past events and reviews marked unsure or not music. Consequently, the `past` filter currently returns no events. Event responses include a hosted `image_url`.

Run `npm install` and `npm test` in this folder. Tests use an isolated SQLite fixture to exercise query logic and HTTP routes. A verified backup was imported into the Hostinger MariaDB staging database, with row counts and SHA-256 comparisons matching all 15 tables at import. The Node migration script, API process, prepared statements, protected edits and a Vilnius Events page import have also been tested against a disposable local MariaDB 11.4 instance. Hostinger serves public event data and an image directly; cross-site image requests from a local web preview encountered Hostinger's CDN challenge.

`npm run test:mariadb` runs the API integration test against a disposable MariaDB database. It requires `MYSQL_TEST_HOST`, `MYSQL_TEST_PORT`, `MYSQL_TEST_USER`, `MYSQL_TEST_PASSWORD` and `MYSQL_TEST_DATABASE`; the database name must end in `_test` and the database must be empty. The test creates schema and fixture rows and leaves them in place. Never use a staging or production database for this test. This test is skipped by the normal `npm test` command unless `RUN_MARIADB_INTEGRATION=1` is set.

Configure the variables in `.env.example` in the hosting environment; never put credentials in the client. `IMAGE_DIR` must point to durable storage outside the deployment directory. `PUBLIC_BASE_URL` is the public API origin. Keep the database private and the administrative token secret.

On Hostinger managed Node.js hosting, do not put `IMAGE_DIR` in `hbuilds/` or `public_html`: [Hostinger documents that these directories are overwritten by deployments](https://www.hostinger.com/support/how-to-deploy-a-node-js-website-in-hostinger/). Verify that a private directory outside those paths is writable by the app, survives a redeployment, and is included in backups before switching the app to the API. Use `127.0.0.1` for a Hostinger database connection as described in [Hostinger's Node.js database guide](https://www.hostinger.com/support/connecting-a-hostinger-mysql-database-to-a-node-js-application/). The API deploy package must not include `.env`, tokens, backup databases, or `node_modules`.

Authenticated endpoints cover the private event list, editor data, image reads and uploads, reviews, details, artist decisions, manual prices, assistant-review confirmation, job leases, MusicBrainz and Vilnius Events imports, and AI evaluation results. They are disabled unless a server-side `ADMIN_TOKEN` is configured, require a bearer token, and update related records in a transaction. Use a long, randomly generated URL-safe ASCII token, never expose it in Expo or browser code, and require HTTPS outside local development. Dedicated rate limiting for administrative requests is not yet implemented; protect and rotate the token if exposed.

`migrate:staging` is a staging-only transfer tool. It checks the backup manifest, refuses database names without the `_staging` suffix and refuses databases containing tables. It creates the schema and compares every copied row with the SQLite backup. The script does not copy images. Database schema creation is not transactional in MariaDB; a failed run can leave empty tables requiring manual cleanup. It has been verified against local MariaDB, but not run on Hostinger. Do not point it at production.

An alternative for an **empty staging database** is `DB_NAME=<database_ending_in_staging> npm run export:staging -- <complete-backup-directory> <new-output-prefix>`. It checks the backup and generates a SQL import file and a separate verification query, without copying images. Both files contain private catalogue information and must be kept out of Git and public directories. Importing the generated SQL into Hostinger's private staging database and running its verification query was tested. Never import into a populated database or production. Staging databases created with the previous schema need migrations `001-auto-increment.sql`, `002-job-leases.sql`, and `003-musicbrainz-jobs.sql` in order before new imports; these have been applied on Hostinger.

To prepare images from the same complete backup, run `npm run prepare:images -- <complete-backup-directory> <new-staging-directory>`. It checks the database hash and each referenced image against the backup manifest, then creates a new `images` directory and a checksum manifest. It refuses an existing destination and removes its newly created directory on failure. After transferring the entire directory, run `npm run verify:images -- <staging-directory>` at the destination to check each file and detect missing or extra files. The 100 image files were uploaded to storage outside the deployment directory; the hosted files have not yet been verified individually against the manifest. One image was retrieved successfully after a redeployment.
